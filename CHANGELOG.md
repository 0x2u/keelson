## [Unreleased]

### Added
- **Update the dashboard in one click**: when the host runs the updater, *Settings → About* offers **Update to vX.Y.Z** beside *Update available*. The dashboard container stays as hardened as before (no Docker socket): it writes a request file into a folder it shares with the host (`DIR/run`, `KEELSON_RUN_DIR` in the container), and a systemd path unit that `install.sh` installs runs `update.sh` as root. The host does not trust the request: it takes only a `vX.Y.Z` version, refuses a version that is not strictly newer than the pinned one (no downgrade) and a `latest` pin, downloads that release's `install.sh` (which copies the database first, pulls and waits for the dashboard to be healthy) and, when the update fails or the new version is not healthy, **rolls back by itself**: the database copy of that run is restored and the previous version comes back. The dashboard accepts only the latest release it has itself found, asks for the unlock, audits the request and shows the progress across the restart (`update-status.json`). Existing installs enable it by re-running the install command once. `update.sh` ships with each release; shellcheck, 489 shell checks (`deploy/tests`) and a real Docker smoke (an update, a refused downgrade and a rolled-back update) run in CI. See [Upgrading](docs/hosting.md#one-click-update).
- **Stop an app without deleting it**: an app's `enabled: false` stops its containers and keeps them (and its configuration, image, variables, volumes, data and history). The agent enforces it on every reconcile and after each configuration change, so a container started by hand is stopped again. Its domains answer `503 This app is stopped.` (nginx: the upstream is marked `down`), a deployment, rollback, build or preview of it is refused with `409`, and a start or restart of its container is refused too: remove the key first. A stopped app is not an incident: no `app.down` alert, no outage in availability or in time to restore service, `keelson_app_up` is left out of `/metrics` (so `== 0` alerts do not fire) and `keelson_app_enabled` says why. `GET /v1/apps` carries `enabled` for every app. The dashboard has **Stop** and **Start** on the app page and on each project card (Stop writes `enabled: false` through the configuration, versioned and audited; Start clears it and starts the container), shows a muted *Stopped* status, counts it out of *needs attention*, *apps up* and the readiness checks about a running app, and disables Deploy, Roll back, Promote and Restart with a reason. Covered by a test against a real Docker engine and a real Caddy. See [Deployments](docs/reference/deployments.md#stopping-an-app).
- **Canary deployments**: an app's `canary:` block (`steps: [10, 50]`, `hold: 1m`) shares the visitors between the version that serves and the new one: 10%, then 50%, then everyone, each step watched for `hold` by the checks of the soak (the container, `health_path`, `verify`) and the metric gates of `analysis`, each step with its own evaluations. A step that fails sends every visitor back to the previous version, which never stopped, and the deployment ends `rolled_back` with the step in its error. Caddy decides by weights and keeps a browser on the version it was given with a cookie, so a page and the hashed assets it points to come from one version; each step is a new draw. The deployment gets a `canary` phase between `switch` and `soak` (the dashboard draws it and edits `canary` in the app form); `analysis` may now run with `soak: 0s` when there is a canary. The apps file refuses a canary with nginx, without a port or domains, with steps outside 1 to 99 or that do not rise, and a gate that a step is too short to trip. The share lives in the agent's memory: an agent that restarts mid-rollout puts every visitor back on the previous version. Covered by tests against a real Caddy and by a real Docker engine and Caddy with fifty browsers asking all along. See [Deployments](docs/reference/deployments.md#canary-sharing-the-traffic-step-by-step).
- **Metric gates**: an app's `analysis:` block lists Prometheus queries (a PromQL expression with `{{app}}`, `{{container}}` and `{{version}}`, `max` and/or `min`, `interval`, `failure_limit`, `no_data`) that the agent asks during the soak. A value out of bounds `failure_limit` evaluations in a row sends traffic back to the previous version, as a failing page does. A failed query counts as bad; a quiet app passes unless `no_data: fail`. The apps file refuses a gate the soak is too short to ever trip. The events of the deployment say what each metric answered; the dashboard's app form has a section to edit them. Covered by a test against a real Prometheus and a real Docker engine. See [Deployments](docs/reference/deployments.md#metric-gates-judging-the-new-version-by-your-metrics).
- **Alerts for what nothing watched**: `certificate.expiring` and `certificate.renewed` (the agent reads, every six hours, the certificate its proxy serves on `127.0.0.1:443` for each of this server's names and warns `cert_warn_days` days before the end, again at 7, 3, 1 and 0), `proxy.drifted` (the proxy no longer served what the agent had applied and was put right; once an hour while it lasts) and, off by default, `dashboard.unreachable` / `dashboard.recovered` for an agent that connects out and loses the link for three minutes. The first three are sent without `events` listing them.
- **Notifications that never got through are sent again**: thirty seconds after channels come into force (every start of the agent, and when a channel is added) the agent sends again the events of its history that reached nobody — `failed`, `dropped` or `no_channel` — if they are less than a day old and have been tried fewer than three times, oldest first. Each record is updated where it is, with how the last attempt went and how many were made. A job that failed before the first webhook existed is therefore announced once it exists.
- **Delivery performance (DORA)**: a **Delivery** page shows the four numbers for the whole fleet over 24 h, 7 d or 30 d — deployment frequency, lead time for changes, change failure rate and time to restore service — with the DORA band each falls in and a line per server. Each agent computes its own from the deployments and outages it records and serves them at `GET /v1/delivery`, exports them on `/metrics` (`keelson_delivery_*`), and records the time of a commit when the caller sends it (`committed_at` on the deploy and build routes; the dashboard sends it on a push and on a workflow run, the deploy action from `github.event.head_commit.timestamp`). The fleet's medians are computed over the durations the agents send, not over their medians. See [Delivery performance](docs/reference/delivery.md).

### Changed
- **A failed deployment stops asking for attention after a day.** Until now, a deployment that ended `failed` or `rolled_back` kept its app on *needs attention* until the next successful one, however old: a rehearsal of a rollback that failed in under a second kept a healthy app flagged for two weeks. It is now flagged for 24 hours, the way an alert that reached nobody is: the agent sent its notification when it happened and the app serves the version it served before. A `rollback_failed` (nothing known to serve), a container that is down and the other items are unchanged, and the deployment stays in the app's history with its status.
- **Longer sessions.** A session now goes idle after 7 days (it was 2 hours) and ends after 30 (it was 12 hours), so the operator signs in about once a month instead of several times a day. Sessions are still server-side, listed on Settings, Security, and revocable at any time.
- **Unlocking sensitive changes is off by default.** The padlock in the top bar, and the password and second factor it asks for before a sensitive change, now only exist with `KEELSON_STEP_UP=on`. Without it a signed-in session makes those changes directly; a stolen session cookie is then as powerful as the operator, which is why [Security](docs/reference/security.md) says to keep sessions to trusted devices and to turn it on if that is a risk. An install that wants the previous behaviour sets the variable once.

### Fixed
- **The GitHub links of the Integrations page.** *Settings on GitHub* no longer points at `github.com/apps/<name>`, the public page of an App, which answers 404 for a private one: it goes to `github.com/settings/apps/<name>` (or the organization's page). *Install on more repositories* is replaced by one *Manage repositories of <account> on GitHub* button per installation, which opens `github.com/settings/installations/<id>` (or the organization's own installation page); the Source page's *install* link opens the list of installed Apps.

## [0.1.0] - 2026-11-12

First public version. Keelson is pre-1.0: expect rough edges (see [limitations](docs/limitations.md)).

### Agent
- One agent per server. It connects out to the dashboard (no inbound port), or you pair it with a one-time code, over SSH, or by file.
- Blue/green deployments with a health gate, drain, soak and automatic return to the previous version. Release steps, including a verified encrypted backup. Rollback and promotion of the exact image.
- Builds on the server, or on another server or a connected computer, with presets for Next.js, Node.js, Vite and static sites. No registry needed.
- GitHub integration: push and pull-request builds, signed webhooks, commit statuses, pull-request previews. A GitHub Action for CI-driven deploys.
- PostgreSQL: declared or managed databases, scheduled `pg_dump` backups with read-back checks, age encryption, local and S3 destinations, retention, guided restore, restore tests.
- Scheduled jobs (HTTP call, host program, one-off container) with overlap protection, history and failure alerts.
- Reverse proxy through Caddy or nginx, with drift detection.
- Notifications to Telegram, a webhook and a heartbeat URL. The last 200 are kept with their delivery status.
- Host load, memory and disk, and container CPU and memory, recorded every 30 seconds for 24 hours (`GET /v1/stats/host`, `GET /v1/stats/history`). App uptime and incidents kept for 30 days (`GET /v1/apps/{app}/availability`).
- Scoped, expiring API tokens, a REST API and an MCP server.
- **`keelson-agent config validate`** checks the apps file and its project files offline, as the agent loads them, with the file and line of each problem (`--format text|json|github`, `--strict` to fail on warnings; exit 0 valid, 1 invalid, 2 usage or an unreadable file). JSON Schemas of the apps file and of the project files, generated from the agent's own structs with each key's documentation as hover text, are in `docs/json-schema/` for completion in an editor ([Configuration](docs/reference/configuration.md#checking-a-file-and-editing-it-with-completion)). CI fails when they are stale, when an example of the documentation does not pass `config validate --strict` and the schema, or when a wrong file passes either.
- **`keelson-agent doctor`** checks a server before or after an install, with a fix for each finding: the Docker engine, the configuration, the files it names (missing, unreadable, a secret readable by every account), the data directory and whether `agent.db` was written by a newer agent, the disks of the data directory and of Docker, Caddy's admin API, notifications and the way to the dashboard for a server that connects out. Exit 1 when something failed.
- **Prometheus metrics**: `GET /metrics` on the agent, in the text exposition format and behind the same token (and client certificate) as the other reads: the engine and the host, and for each app whether it is up, its restarts, its last deployment, and for each job and backup when it last ran and succeeded, plus the proofs the agent has seen (a restore tried, a key proven). A part that cannot be read leaves its series out and says so in `keelson_collector_success`. `docs/examples/prometheus` has a scrape configuration and alert rules with unit tests; CI lints a real agent's answer and tests the rules with `promtool` ([Metrics](docs/reference/metrics.md)).

### Dashboard
- First-run setup, projects and environments, forms and a YAML editor with validation, diff, versions and restore, an audit log, a readiness checklist, and a domains wizard with Cloudflare DNS.
- New projects from an image (no GitHub needed) or from a repository.
- Charts for resources over time, per-app availability, CPU and memory, a deployment summary, alert history in Activity, and memory and load in the server list.
- Two-factor authentication, passkeys, step-up unlock, sessions and an IP allowlist. Secrets are write-only.
- Settings, About shows the latest release and the command to update. The dashboard asks api.github.com for it once a day and sends nothing about your servers; set `KEELSON_UPDATE_CHECK=off` to turn it off.
- The Update page of a connected server shows whether the update worked.
- **A visual identity.** The Keelson mark (two frames of a hull over the keel) and its name in the sidebar, on the sign-in and setup pages, as the favicon and the app icon; a palette built on the mark's cyan and ink in both themes (the dark theme's primary action, focus ring and active tab are the brand cyan; every text pair still passes WCAG AA); Sora for the name and page titles, served from the repository. The logo files, colours and rules are in [`docs/brand`](docs/brand/README.md).
- **A layout of its own.** Home opens with the state of the fleet said once and large (an orb, the headline, apps up, deployments and backups) and the last 24 hours as 24 hourly bars, computed from the same data as the lists below; server tiles show disk, memory and load as gauges that stay neutral until a measure needs a look; the pipeline of a deployment is a connected rail; project cards have a state hairline and an environment rail; section titles, table headers and summary cards read as instrument labels in the display face; the active tab and sidebar item take the brand. The main area can now shrink, so a wide table scrolls inside its card instead of pushing the page sideways.

### Install
- One-command dashboard install (`deploy/install.sh`, compose, Caddy). Re-running it with `--version vX` updates an existing install: it keeps `.env`, the data volume and the master key, and copies the database to `<dir>/backups` first.
- Multi-architecture release images and agent binaries, built by the release workflow (with a dry-run mode).
- A failed agent upgrade is rolled back, including the agent database.

### Testing and CI
- CI runs the agent tests and the real-engine tests on amd64 and arm64 runners. New real-engine tests break a deployment on purpose: a release that exits at once never takes the site down, and an agent killed in the middle of the swap (old container renamed and no new one yet; new container started and not yet judged) comes back on the previous version and closes the deployment as rolled back. A frozen `agent.db` written by v0.1.0 must open, migrate and keep its history in every later version.
- `scripts/demo-rollback.sh`: a deployment that fails, on your machine with only Docker and Go: version 2 of a site cannot start, the agent puts version 1 back and the script checks that it serves again. It runs in CI on both architectures.

### Security
- The agent is built with Go 1.27.4, which fixes GO-2026-6859 (CVE-2026-97054) in `net/http`: an HTTP/1 server using `MaxBytesReader` could crash when its handler read the request body while writing the response header. The agent's enrolment route is one such handler. CI's `govulncheck` caught it; `agent/go.mod` now requires the fixed version.
