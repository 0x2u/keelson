# Builds

An app is built by the agent that runs it, or by any other server or connected computer with enough memory. Nothing builds unless the app has a `build:` block and the build is switched on in the dashboard. An app without a Dockerfile can use a [preset](#build-presets-no-dockerfile-in-the-repository). Images are never pushed to a registry: they are tagged `<image>:<commit sha>` locally and, when built elsewhere, copied to the server that runs them.

## Building on the server from a GitHub App

An app opts in to building on its own server with a `build:` block. The dashboard's GitHub App (see [Hosting](../hosting.md#github-app-build-and-deploy-from-pushes-and-pull-requests)) then has this agent build and deploy each pushed commit, with no CI workflow. The dashboard hands the agent a short-lived URL and token, and the agent downloads the source itself (the dashboard is not on the data path and the agent needs no `git`). It builds with Docker, tags the result `<image>:<commit sha>` locally and deploys it through the usual pipeline: release steps, health gate, rollback. Nothing builds unless you add the block and also turn the build on for the app in the dashboard.

```yaml
apps:
  - name: shop
    image: ghcr.io/acme/shop           # the repository the build is tagged as; the tag is the commit sha
    build:
      dockerfile: Dockerfile         # relative to context (default Dockerfile)
      context: .                     # a subdirectory of the repository (default .)
      target: runner                 # optional multi-stage target
      args: { NODE_ENV: production } # build arguments: NOT secret
      timeout: 15m                   # default 15m, at most 1h; covers the download too
      memory: 2g                     # memory of the build's containers, swap included (default 2g)
      cpus: 2                        # CPU cap of the build's containers, in cores (default 2)
      network: host                  # optional: build on the server's own network (default: the engine's bridge), see Limits of a build
      platform: linux/amd64          # optional: the platform to build for, linux/amd64 or linux/arm64 (default: the engine's own)
      max_source: 512m               # a larger source archive is refused (default 512m)
      source_hosts: [api.github.com, codeload.github.com]   # where the source may come from (default these two)
```

- One deployment covers both phases. Its trigger is `build` (`preview` for a preview), and its events log `downloading source`, `building`, the build output, `built <ref>`, then the usual deploy events. The output is bounded: the first 2000 lines (256 KiB) as they come, then only the last 2000 (256 KiB) after a notice of how many were omitted, so a build that fails late still ends with its reason. A failed build (or a refused archive, a timeout, an unreachable source) fails the deployment with that reason, deploys nothing and leaves the serving version untouched. `GET /v1/deployments/{id}` reports it like any other.
- The image exists locally, so the deployment does not pull. A rollback to a version that was built here works for as long as its image is kept (`keep_images`); if it is gone, the rollback fails with that explanation and the serving version stays. Old images are removed after a successful deployment as for any app.
- An agent runs one build at a time. A second request answers `409` (the dashboard retries on the next push). Builds go through the Docker engine's API, so the agent needs no Docker CLI.
- Source: only `https`, only a host listed in `source_hosts` (an exact host name; for GitHub Enterprise Server list its host, and its codeload-like host if it has one). A redirect is followed only to those hosts and to `codeload.github.com`, never to `http`, and the `Authorization` header is dropped as soon as the host changes. The archive must be a gzip tar with GitHub's layout (everything under one top-level directory, which is stripped) and at most `max_source` big, and its files may not add up to more than 8 times that. The `context` subdirectory is sent to Docker and only it. The agent refuses an absolute path, a `..`, a symlink or hard link that points outside the context, an entry below a symlink, device files and pipes; setuid and setgid bits and ownership are cleared. An archive that is refused is never built, not even partially.
- The token is held in memory for the download and nowhere else: not logged, not in SQLite, not in an event, an error, the audit log (which records the app and the commit), a process argument or a container's environment.
- Limits of a build: `memory` and `cpus` cap the build's containers (the engine's `--memory` with no swap, `--cpu-quota`); they are not privileged, run on the default bridge network, and see no host path and no Docker socket. Size `memory` from a measurement, not from the 2g default. A Next.js `next build` of a real application was killed by the kernel at 1.9 GiB while type-checking (exit 137) and succeeded with `memory: 3g`, peaking at 2.67 GiB. The cap kept the server's other site answering throughout. A step that runs past `timeout` is abandoned and the engine removes its containers. The engine's own builder is used (not BuildKit): `RUN --mount`, `# syntax=` and other BuildKit-only features are not available, and base images are pulled anonymously when missing (a base image from a private registry must already be on the server). The classic builder commits a layer per instruction, walking the whole filesystem: declare `ARG`/`ENV` lines before the big `COPY` steps, or each costs seconds. Build-time credentials are not supported: build arguments are visible in the image history and in this file, and no secret reaches a build (no BuildKit secrets, no registry credentials, none of the app's `env`).
- `network` (optional, empty by default) is the network the build's containers run on: the default bridge, `host` (the server's own network), or the name of a user-defined Docker network. `host` is for a build that has to reach something only the server sees, such as a framework that queries a PostgreSQL on `127.0.0.1` while it builds: the Dockerfile's code then sees every port the server listens on, so enable it only for a repository you trust to that level. A named network gives the build the containers on it and no more (`none`, `bridge` and `container:` are refused). The dashboard has `host` as *Build on the server's network* in the app's Build section.
- `platform` (optional, `linux/amd64` or `linux/arm64`; default: the engine's own platform) is built with the `docker` command (BuildKit: `docker build --platform …`, the context on its standard input, build arguments in its environment, never on the command line), which must then be in the agent's `PATH`. The engine's own classic builder cannot do it on a Docker Desktop that stores images with containerd (it fails exporting the image with `content digest … not found`), and BuildKit does not take `memory` and `cpus`: the limits of the machine's Docker apply. A build without `platform` keeps using the engine's builder. It is for a build machine of another architecture than the server that runs the image: an Apple-silicon Mac builds `linux/arm64` unless told otherwise, and most servers are `linux/amd64`. The base images are then pulled for that platform, and a `RUN` step of the other architecture runs emulated, which is slow. Whatever the platform, `PUT /v1/apps/{app}/image/{tag}` reads the image config of the archive it receives and refuses it with `422 {"error": "image is for linux/arm64 but this server runs linux/amd64"}` when its architecture or operating system is not the engine's (`GET /v1/system` says which), before anything is loaded; an archive without a readable image config is refused with `400`.
- `database: true` (optional, off by default) lets a build use the app's managed database (see *Managed PostgreSQL*), for a build that queries its database to build (static pages filled from it) on a database that was just created and is empty. The database's URL is then also passed to the build as a build argument, whether or not its variable is flagged for builds (the agent still refuses to flag it: this option is the explicit way), and the build runs on the network that reaches it: the server's own network for an app on it (its URL is on loopback), the managed PostgreSQL's network (`keelson`) otherwise, unless `network` names another. It is the one case where a managed database's password reaches a build: it is scrubbed from the build's output, but it stays in the build's own layers on this server (never in the image that runs, for a multi-stage Dockerfile, and nothing is pushed anywhere). The database is new and has no tables, so the Dockerfile must create them before the build queries them (for Prisma, `RUN prisma migrate deploy` when `DATABASE_URL` is set). A preview never gets it. The dashboard has it as *The build uses the app's database*, and *New project* sets it when it creates a database with the project.
- `KEELSON_BUILD_DATABASE`: with `database: true`, until the app has had a successful deployment, the build also gets this build argument, set to `1`. It tells a Dockerfile that its database is one the agent made and that holds nothing yet, so it may create the tables before it builds (for Prisma, `prisma migrate deploy` when it is `1` and `DATABASE_URL` is set). After the first successful deployment the database holds data and the argument is gone: the build still reads the database (URL and network are unchanged), and migrations belong to a release step, which comes after the backup. (Before this rule the argument was set on every build: a migration that failed in a build was recorded in the live database and refused every deployment after it.) Without `database: true` it is never set, so a build that reaches a database holding data (a native production one, through a variable flagged for builds) must never migrate it either. A build that reads a table a new migration creates therefore fails until the migration has run: deploy the migration first, or keep the build's reads to what the previous schema has.
- A build runs the repository's Dockerfile on this server. Enable it only for repositories you trust to the level of the server's Docker engine; fork pull requests never build (the dashboard does not ask).
- Disk: the engine keeps the layer cache of builds. It speeds up the next build and slowly fills the disk, so run `docker builder prune` or `docker image prune` now and then. The agent only removes the tagged images of the apps it deploys; it never prunes the engine's cache.
- Previews inherit the parent's `build:` block: `PUT /v1/previews/{app}/{pr}` with `{"sha":"<40 hex>","source":{"url":...,"token":...}}` instead of `{"tag"}` builds `<image>:<sha>` with it and deploys the instance (exactly one of `tag` or `sha` with `source`). The same single build slot applies. It is checked first, so a refused request evicts and creates nothing.

See [`examples/build.apps.yaml`](../examples/build.apps.yaml).

## Building on one server, running on another

A small server may not have the memory to build (a Next.js build peaked at 2.67 GiB). Any server can build for another, and nothing has to be declared on the build server. The app that runs the image keeps its `build:` block. The dashboard sends that block to the build server as a request and then moves the image.

```yaml
# on the build server's agent (optional: without it the default ceilings apply)
build_limits: {memory: 6g, cpus: 2, timeout: 30m, host_network: false, keep_images: 3}
```

- **`POST /v1/builds`** (signed, audited `build`): `{"app", "image", "sha", "source": {"url", "token"}, "build": {…the app's build block, without `only` and `database`…}, "port"?, "health_path"?}` answers `202 {"deployment_id"}`. The server builds `<image>:<sha>` locally (never pushed) and records a `trigger=build` deployment under `app`; it ends `succeeded` with `… built here and runs elsewhere: nothing is deployed on this server`. No app is needed in this server's file. If its file has an app of that name with another image, or another app using the same image repository, the request is refused (`409`, a name collision). Omit keys you do not set: a missing key takes the lower of the default and the server's ceiling; an empty value counts as stated.
- `build_limits` are enforced for these requests: memory, cpus, timeout, max_source, source_hosts (the request's hosts must be within the allowed ones), `network: host` only with `host_network: true`. A request above a limit is refused with `400`, naming the limit. It is never clamped. `GET /v1/system` carries `build: {enabled, limits}` (`memory` 0 = no ceiling), which is how the dashboard knows a server can build and how big. An app's own build on its own server (`POST /v1/apps/{app}/build`) is unchanged and not limited by `build_limits`.
- Build variables live on the build server and are write-only. A remote build uses the request's `build.args`, then the **build variables stored on the build server for that app name**, then (the existing behaviour) the app-scope variables flagged for build under the same name there. The dashboard never sends or reads back a secret: `PUT /v1/build-vars/{app}` (signed, `{set: {NAME: value}, remove: [NAME]}`, same name and size rules as the environment API; works for an app that is not in this server's file and on a connect machine), `GET /v1/build-vars/{app}` (read token: `{names: [{name, changed_at}]}`, never a value) and `DELETE /v1/build-vars/{app}`, stored in `<data>/env/<app>.build.env` (0600), audited by name (`build_vars.set`, `build_vars.remove`) and scrubbed from the build output like any build argument. The build log says how many were used. The dashboard shows them under *Source → Build on → Build variables on <builder>*. The app's own build variables on the server that runs it are not used by a build elsewhere (the card names them). `build.args` entries whose name looks secret (`token|secret|passw|key|credential`) are hidden by `GET /v1/config` and so left out of the request: put them in the build variables. `build.network: host` is sent when the build server allows it (`host_network: true`), refused before sending otherwise; a named network and `database` are never sent. As with any build argument, a single-stage Dockerfile keeps the value in the image history.
- Three signed routes move the image. `POST /v1/images/export` with `{"image","tag"}` (and `POST /v1/apps/{app}/image/export` with `{"tag"}`) streams the image as a tar archive, only if this server built or received it (never an arbitrary image the engine holds). `PUT /v1/apps/{app}/image/{tag}?sha256=<hex>` receives one: the archive goes to a private staging directory while its SHA-256 is computed, which must equal the one in the **signed** address (the signature covers the request without a body, so a multi-hundred-megabyte archive is never held in memory to be signed), then its `manifest.json` is read and must tag exactly one image, exactly `<image>:<tag>` of that app before anything is loaded. It is refused while the app is deploying, up to 8 GiB, and the image is recorded as local: deploying it does not pull. A server that connects out can receive it too: the relay carries the body as a stream (see below).
- The dashboard drives it. On the app that runs the image, *Source → Build on* lists the servers as cards, each with its CPUs, load, free memory, disk and its build limits, and says whether a build of that size fits now; a server over a limit, offline, without a deploy secret or with an agent that predates `/v1/builds` is shown disabled with the reason (*update the agent on X*). Then **Deploy**, or a push with *Deploy each push*, sends the request, and when the build succeeds the dashboard downloads the archive from the build server and sends it to the server that runs the app (the SHA-256 is computed on the way and signed), and deploys the tag there, recorded with the trigger `transfer` (*Built on another server*). `build.platform` is set from the target's architecture when the builder's differs (a note says it is built through emulation). `database` is not sent, and `network: host` only when the build server allows it (see build variables above). The commit status `keelson/build` covers the whole journey; the audit log records `build_transferred` or `build_transfer_failed` with the step that failed. A build that fails sends nothing; an image the other side refuses is not deployed; the app keeps serving its previous version in every case. The journey runs in the dashboard's process: if the dashboard restarts in the middle, press *Deploy* again.
- Cost: the archive passes through the dashboard. For an image of 200 to 400 MiB that is one more copy on the dashboard's disk (a temporary file, deleted afterwards) and the time to move it twice. A build that queries a database on the other server needs its own route to it (an SSH tunnel to a read-only role, say).


## Build presets: no Dockerfile in the repository

With `build.preset` the agent writes the Dockerfile itself, so a repository does not need one. You choose the preset (the dashboard shows them as cards); nothing is detected from the repository. A preset replaces `dockerfile:` and `target:`, which are refused next to it.

```yaml
    build:
      preset: nextjs          # nextjs | node | vite | static
      install: pnpm install --frozen-lockfile   # default by lockfile, below
      build_command: pnpm run build             # default: <package manager> run build
      start: node server.js   # nextjs and node only; defaults below
      output_dir: dist        # vite and static only (default dist)
      node: "22"              # Node.js major version (default 22, 18 or later)
      spa: true               # vite and static only (default true)
      standalone: false       # nextjs only (default false)
```

| Preset | Builds | Runs | Defaults |
|---|---|---|---|
| `nextjs` | `next build` with `node:<version>-alpine` | `next start -p $PORT` through the package manager, as the `node` user; with `standalone: true` the image holds only `.next/standalone`, `.next/static` and `public` and runs `node server.js` (your `next.config` needs `output: "standalone"`; the build fails with that message when it is missing). The standalone image is several times smaller. | `build_command: <pm> run build`, `start: <pm exec> next start -p "$PORT"` |
| `node` | the `build` script if `package.json` has one | `<pm> start` as the `node` user | `start: <package manager> start` |
| `vite` | `<pm> run build` with Node.js | the built `output_dir` served by nginx as the `nginx` user | `output_dir: dist`, `spa: true` |
| `static` | nothing, or `build_command` with Node.js when you give one | `output_dir` served by nginx as the `nginx` user; `.` serves the whole repository | `output_dir: dist`, `spa: true` |

- The package manager comes from the lockfile at the root of the build context: `pnpm-lock.yaml` (`pnpm install --frozen-lockfile`), `yarn.lock` (`yarn install --frozen-lockfile`), `package-lock.json` (`npm ci`), none (`npm install`); `pnpm` and `yarn` run through Corepack, which honors the `packageManager` field of `package.json` (its cache is carried into the runtime image, so the container needs no network). `package.json` is required (except for `static` without a build); the manifests, the lockfile and `.npmrc`, `.yarnrc`, `.yarnrc.yml`, `pnpm-workspace.yaml` are copied before the sources, so the install layer is reused while they do not change. A postinstall script that needs your sources is therefore best served by an explicit `install` (`npm ci --ignore-scripts`). Workspaces and monorepos are not understood: point `context` at one package, or write your own Dockerfile.
- The port is the app's `port:` (or, without one, 3000 for `nextjs` and `node`, 8080 for `vite` and `static`): the image sets `PORT` (and `HOSTNAME=0.0.0.0` for Node.js) to it and exposes it. With `port.host`, `port.env` must be `PORT` (its default), which the generated images read at start. nginx runs as a regular user, so `vite` and `static` need a port of 1024 or more.
- The image has a `HEALTHCHECK` (busybox `wget` on `http://127.0.0.1:$PORT<health_path>`, `/` without a `health_path`); `health_path` may only hold letters, digits and `. _ ~ / % ? & = : @ + , -` with a preset.
- The image is multi-stage and does not run as root, uses `tini` as init for the Node.js images (a Node.js process alone as PID 1 ignores `SIGTERM`, so a stop would wait for the kill), and sets `STOPSIGNAL`. The Node.js runtime image carries the project as built, dev dependencies included: the `standalone` Next.js image is the small one. nginx serves with the agent's own configuration: dotfiles are never served, `/assets/` of `vite` is cached for a year (Vite names its assets after their content), `spa: true` answers unknown paths with `/index.html`, `spa: false` with 404.
- Build arguments (`args:`) are declared as `ARG` in the build stage, so `NEXT_PUBLIC_*` values reach `next build`. They stay out of the runtime stage, but visible in the image history: never put a secret there.
- `install`, `build_command` and `start` run through `sh -c`, one line, at most 1024 bytes, no control characters; they reach the Dockerfile in its JSON (exec) form, so no value can end an instruction or start another. `output_dir` is a relative path of letters, digits and `. _ / -`, `node` a major version.
- The Dockerfile is `.keelson.Dockerfile`, added to the build context next to a `.dockerignore` (`.git`, `.next`, `node_modules`) when the repository has none. A repository that already has a file or directory of that name is refused: so nothing of the repository is overwritten. Previews inherit the preset with the rest of the block.
- The build needs the network: the engine pulls `node:<version>-alpine` (or `nginx:alpine`), and the build reaches the npm registry, Corepack's downloads and Alpine's package index (for `tini`).

Examples: [`nextjs`](../examples/preset-nextjs.apps.yaml), [`node`](../examples/preset-node.apps.yaml), [`vite`](../examples/preset-vite.apps.yaml), [`static`](../examples/preset-static.apps.yaml).

## Linking an app to its repository

A `source` block says which repository an app is built from. The agent only checks its shape. The dashboard reads it to deploy when a CI workflow succeeds or to build a push or a pull request, and writes it when you link an app on its *Source* page. Saving it creates a configuration version and needs no redeploy.

```yaml
apps:
  - name: shop
    source:
      repo: acme/shop                 # owner/name
      branch: main                    # the branch the app follows
      deploy_on: workflow             # deploy when the workflow below succeeds; leave out for manual deploys only
      workflow: CI                    # the workflow whose success deploys the app (required with deploy_on)
      previews_workflow: Preview      # the workflow whose success on a pull request builds its preview (leave out: no previews)
      build_on: [push, pull_request]  # events that build the app on a server; leave out: nothing builds by itself
      build_server: build-1           # the server that builds, as the dashboard names it; leave out: the app builds where it runs
```

The GitHub side (webhook, GitHub App, what triggers what) is in [Hosting](../hosting.md#github-webhook-automatic-deploys-and-previews).
