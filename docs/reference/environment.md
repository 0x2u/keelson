# Environment variables and secrets

Variables can be written in the apps file (`env`, `env_file`) or set through the API, which is what the dashboard's *Variables* page does so that an operator never needs a shell on the server. Both are for **the app's runtime**; the apps file is not changed by the API.

- **Where they live.** In files under `<data-dir>/env/` (the directory is `0700`): `<app>.<scope>.env`, mode `0600`, replaced atomically (a temporary file in the same directory, flushed, then renamed, so a crash leaves the old file or the new one, and a reader never sees half of a change). The file is a dotenv file with a `# keelson-env v1` header: every value is a JSON string, so a multi-line or quoted value (a private key) survives, and `ReadEnvFile`, the agent's own reader, parses it back. Beside each key, comment lines keep when it changed and whether it is a build argument; the time the scope last changed is there too. **No value is ever written anywhere else**: not in the agent's database, its log, the audit log, a deployment's events, an error, a process argument or an API answer. A permission drift (a directory restored from a backup with another umask) is repaired when the agent starts.
- **Write only.** Once saved, a value is never sent back: `GET` lists the key names, when each changed, whether it is a build argument, and whether it **shadows** a value of the apps file. The only way to read a value is on the server, in the file.
- **Two scopes.** `app` is the running app (its container, its release steps, its one-off container jobs and the app variables a job reads its bearer secret from). `preview` applies to **every preview instance of that app** and only to them: an instance never gets the parent's `env_file`, `env` or `app` scope, and the app never gets the `preview` scope. A preview's environment is the template's `env_file`, then the template's `env`, then the `preview` scope.
- **Precedence** for an app: `env_file`, then `env`, then the stored `app` variables (the store wins: it is what the UI edits). The environment is computed **when a deployment starts**, in one read of the scope, and shared by the release steps and the container: a change made while a deployment runs does not reach it (and cannot corrupt it), and the next deployment gets it. A running container never changes: **a change needs a redeploy**. The listing of apps carries `env_changed_at`, to compare with the serving deployment, so the dashboard can say that a redeploy is due.
- **Build arguments.** `build` in a change is the exact list of keys that are *also* passed as `--build-arg` in builds of the app (a [build on the server](./builds.md#building-on-the-server-from-a-github-app)); left out of the request, the flags stay as they are. The classic Docker builder is used, so a build argument is **not secret**: it stays in the image's history. They are merged under the `build.args` of the apps file, which win, and a preview's build uses the `preview` scope. The agent scrubs them from the build output and from errors (values of 6 characters or more; shorter ones such as `true` or `3000` would garble the log), and removes the URL from a failed engine request, which is where they travel.
- **Rules**, all checked before anything is written (a refusal lists every problem): a name matches `[A-Za-z_][A-Za-z0-9_]{0,127}`; `PATH`, `HOME`, `HOSTNAME` and anything starting `KEELSON_` are reserved; so is `PORT` for an app that has `port` (the agent controls the port; with `port.host` also the variable `port.env` names); a value is at most 32 KiB without a NUL character; a scope holds at most 200 variables and 256 KiB of names and values; a `build` key must exist once the change is applied. If a key becomes reserved after it was stored (the app later got a `port`), it is left out at deployment and the deployment's log says so, by name.
- **Audit.** `env.set`, `env.unset` and `env.delete`, with the app, the scope and the key names. A key that is not a valid name (someone pasted `NAME=value` into the key field) is counted, not copied.
- **Apps removed from the file.** Their stored variables are **kept** (adding the app back brings them back), not served (`404`, with `orphan_scopes` naming what is still stored) and removed by an explicit `DELETE`. A change of the apps file, a restore of one of its versions, or a hot reload never touches them.
- **Backups.** The directory holds secrets in clear text, like an `env_file`: back it up as carefully as the data directory it sits in.

## Routes

| Route | Auth | Description |
|---|---|---|
| `GET /v1/apps/{app}/env?scope=` | read token | The names of the variables stored for the app, never a value: `{"scope","vars":[{key,updated_at,build,shadows}],"last_changed"}`. `scope` is `app` (default) or `preview`. `shadows` is `"env"`, `"env_file"` or `null`. `404` for an app that is not in the apps file (with `orphan_scopes` when variables of it are still stored), `400` a bad scope. See [Environment variables and secrets](#environment-variables-and-secrets). |
| `PUT /v1/apps/{app}/env` | signature | `{"scope":"app","set":{"KEY":"value"},"build":["KEY"],"unset":["OLD"]}` -> `200 {"scope","changed":[keys],"removed":[keys]}`. All or nothing: `400 {"error":"invalid","message","issues":[{"key","message"}]}` lists every problem and writes nothing. The body may be up to 2 MiB on this route (64 KiB elsewhere). Audited as `env.set` or `env.unset`, with key names only. |
| `DELETE /v1/apps/{app}/env?scope=` | signature | Removes every stored variable of the scope: `200 {"scope","removed":[keys]}`. For an app no longer in the apps file it deletes the orphaned file instead. Audited as `env.delete`. |
